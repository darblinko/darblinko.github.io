Checking LLM-generated Cypher before it reaches a multi-tenant graph

cypher-guard is a Python check that runs between a language model that writes Cypher and a Neo4j graph shared by several tenants. It rejects writes and requires every node and relationship variable to be compared with $org_id in the clause that binds it. At revision 657c31f it rejects 79 of 79 adversarial queries with the expected error code and accepts 31 of 31 valid ones. The guard as first committed, at 502b403, accepted 19 of those adversarial queries, and on Neo4j 5.26.12 the result of each of the 19 depends on another tenant's data.

The model writes the query; the caller supplies the tenant

An agent that answers questions from a graph database often lets the model write the query. In the data model cypher-guard assumes, every node and relationship carries an org_id property, and one query runs for one tenant. A generated query that leaves out a single org_id comparison can return rows that belong to another tenant.

cypher-guard runs before the query reaches the driver. validate_read_query either raises CypherGuardError with a stable code or returns the query with a row cap added. The caller sends the returned text in a read transaction and binds $org_id from the authenticated request. The guard checks that every binding is compared with that parameter. It cannot check which value the caller binds.

The repository is licensed Apache-2.0, copyright Nysara Global LLC, and has no runtime dependencies. Its first commit, 502b403, imports the guard from a private source. Up to eb95150, the 25 commits after it split the guard into modules, move the test queries into a JSON corpus, add three benchmark scripts and fix the bypasses described below. This article describes the public repository only.

Three passes over tokens, with no Cypher grammar

flowchart TD
  query["Generated Cypher"] --> lex["Tokenize once: strings become placeholders, comments dropped"]
  lex --> rules["Token rules: writes, procedures, functions, UNION, pattern comprehensions, statements"]
  rules --> walk["Scope walker: clauses, bindings, visibility, subqueries"]
  walk --> limit["LIMIT cap per UNION branch"]
  limit --> schema["Schema check, optional"]
  schema --> driver["Neo4j read transaction, org_id bound by the caller"]
  lex -.->|"PARSE_ERROR"| reject["CypherGuardError with a stable code"]
  rules -.->|"code"| reject
  walk -.->|"code"| reject
  schema -.->|"SCHEMA code"| schemareject["CypherSchemaError"]

The guard does not build a syntax tree. The tokenizer reads the source once, left to right. It drops comments, replaces each string literal with a placeholder token, and raises PARSE_ERROR on input it cannot tokenize with certainty: an unterminated string or comment, unbalanced brackets, or, outside strings, comments and backtick-quoted names, any character other than ASCII letters, digits, ASCII whitespace and the Cypher operator characters. A literal such as 'MATCH (n) DELETE n' reaches the rules as one placeholder token.

The token rules scan the whole stream and reject:

  • a write or administrative keyword outside a string: CREATE, MERGE, SET, DELETE, REMOVE, DROP, USE, GRANT, REVOKE, DENY, SHOW, TERMINATE, ALTER, and the sequences DETACH DELETE, LOAD CSV, IN TRANSACTIONS and FOREACH (WRITE_CLAUSE_REJECTED, or SUBQUERY_WRITE inside a CALL { } body);
  • a procedure outside the allowlist, which by default holds only db.index.vector.queryNodes (FORBIDDEN_PROC), and an index argument to that procedure that is not a parameter (VECTOR_PROC_LITERAL_INDEX);
  • a namespaced function outside the built-in namespaces date, datetime, localdatetime, localtime, time, duration, point and vector (FORBIDDEN_FUNCTION);
  • UNION unless the caller passes allow_union=True (UNION_DISALLOWED);
  • a list comprehension whose body contains a graph pattern (PATTERN_COMPREHENSION_REJECTED);
  • a semicolon anywhere but at the end, so one call runs one statement (PARSE_ERROR).

The scope walker splits each UNION branch into clauses and tracks visible variables the way Neo4j does. WITH and RETURN replace the visible set with their projection. Each UNION branch starts empty. A CALL { } body sees only the names its leading WITH imports. The walker checks the bodies of EXISTS { }, COUNT { } and COLLECT { } with the names visible where they appear. It also rejects an anonymous node (ANONYMOUS_NODE), an OR in a WHERE that mentions org_id (OR_WITH_SCOPE_PREDICATE), and a variable-length relationship without an upper bound of at most 5 (VARLEN_DEPTH) or without a named path whose nodes and relationships all carry an org_id predicate (VARLEN_INTERMEDIATE_UNSCOPED).

The optional schema check compares labels, relationship types, properties and (label)-[TYPE]->(label) triples with a snapshot of the live schema, so a misspelled label raises SCHEMA_UNKNOWN_LABEL instead of returning zero rows.

A binding is scoped only by the clause that introduces it

Every node or relationship variable that a MATCH, OPTIONAL MATCH or YIELD introduces is a new binding, even when an earlier binding had the same name. The binding is scoped only when that clause proves org_id = $org_id for it. Two forms count: an inline {org_id: $org_id} map in the clause's pattern, or an alias.org_id = $org_id conjunct in the clause's own WHERE with no OR above it. A later MATCH or a WITH ... WHERE cannot scope an earlier binding. The repository gives two reasons: an OPTIONAL MATCH does not remove rows, and any clause in between may already have read, sorted or aggregated rows from other tenants.

After WITH count(a) AS n, the name a is out of scope, and the second MATCH binds every Ticket in the graph. The guard at 502b403 recorded scoping per alias name across the whole query, so the scoped first a covered the second. On the two-tenant seed the query returns 4 ticket titles, and one of the 4 tickets belongs to tenant-b. At 657c31f the second a is a new binding with no scope, and the guard raises UNSCOPED_ALIAS. This code rejects 32 of the 79 adversarial rows, more than any other code.

The strict rule rejects some queries that Neo4j would filter correctly in the end, and the README lists it as a design decision. YIELD node, score from the vector procedure is one case: score is a yielded binding with no scope, so the accepted form yields node only.

Three of the classes show how a token-level check can disagree with the database about where a construct ends:

  • Comment inside a string. The first lexer removed comments with a regular expression before it removed string literals. In WHERE n.email <> 'x//' MATCH (m:Ticket) RETURN DISTINCT m.title the guard read // as the start of a comment and never saw the unscoped MATCH (m:Ticket). Neo4j read the string and ran the whole query.
  • Operator read as a clause. The clause splitter treated the WITH of STARTS WITH as a new clause. In WHERE t.org_id = $org_id AND t.title STARTS WITH 'T' OR true the WHERE body ended at the operator, and the OR true after it was never checked.
  • Query inside a function. apoc.cypher.runFirstColumnMany('MATCH (t:Ticket) RETURN t.title', {}) runs a nested query that the guard sees as one string placeholder. With APOC 5.26.12 the result of the row depends on tenant-b data. The fix rejects every namespaced function outside the built-in namespaces.

The row cap applies to the last projection of each branch

validate_read_query returns the query with a row cap. A UNION branch whose final projection has no LIMIT gets LIMIT 100, and a larger final LIMIT is clamped to 100. A caller may pass a limit from 1 to 1000 in place of 100; any other value falls back to 100. A final LIMIT that is not a single integer literal, such as LIMIT $n, raises PARSE_ERROR. A LIMIT inside a subquery or on a WITH is left as written, because it does not bound the result.

The injector at 502b403 missed four cases. Commit d921520 lists them, and importing each revision's guard reproduces them:

Live run on Neo4j 5.26.12 with two tenants

The corpus counts show which rows the guard rejects. They do not show which rejected rows would have read another tenant's data. benchmarks/live_check.py measures that on Neo4j 5.26.12 community with APOC 5.26.12 and a seed of two fictional tenants: tenant-a with 7 nodes and tenant-b with 3. Every node and relationship in the seed carries org_id, and no relationship joins the two tenants.

Each row runs twice, each time in a transaction that is rolled back: once on the full seed and once after the tenant-b nodes are deleted. A row whose two results differ depends on tenant-b data. Adversarial rows run without the guard, to show what it prevents. Valid rows run as the guard rewrote them.

  • 19 of 19 bypass rows depend on tenant-b data.
  • 31 of 31 valid rows do not.
  • 10 of 37 original rows and 2 of 23 coverage rows depend on tenant-b data.
  • 22 of 37 original rows return the same result with or without tenant-b. The rules reject these rows for their shape. The README labels its explanation an inference: on a seed without relationships between tenants, an unscoped element reached only through a tenant-a node holds no tenant-b data.
  • 19 adversarial rows, 5 original and 14 coverage, raise a Neo4j error or cannot be compared. One example is SHOW DATABASES, which Neo4j refuses in a transaction that has already written.

The run was recorded on 2026-10-28 and was not repeated for this article.

Vector search ranks before the tenant filter

One leak is documented in the repository and not fixed. The valid row yield-renamed-output asks the vector index for the 3 nearest tickets and keeps those of the caller's tenant:

For the query vector [1.0, 0.0] the index returns a-t1, b-t1 and a-t3. tenant-b's ticket ranks second, and the tenant filter leaves 2 rows. The row count tells a tenant-a caller that another tenant holds a closer vector.

The differential run cannot detect this. Inside the transaction that deleted tenant-b, the index returned a-t1 and a-t3 and did not refill to 3. Both runs therefore return the same 2 rows, and the row is recorded as independent of tenant-b. Inference: closing the leak requires the database to filter by tenant before it ranks, which a check of the query text cannot arrange.

Limits of this result

  • Token level, fail closed. Without a grammar the guard rejects some valid Cypher: CALL (x) { } scope-clause syntax, quantified path patterns, non-ASCII names, a final LIMIT that is not an integer literal, and a variable named starts or ends followed by a WITH clause.
  • The corpus bounds the claim. 79 adversarial rows show that these query shapes are rejected. They do not show that no other shape passes. The first version rejected all 37 of its own adversarial tests and still accepted the 19 bypass rows.
  • Fixed names. The property is org_id and the parameter is $org_id. Neither is configurable.
  • Data model. Every node and relationship must carry org_id. The seed has no relationship between tenants, and the rows the guard accepts have not been measured on a graph that has such relationships.
  • Admin procedures. allow_admin_procs=True adds db.schema.visualization and apoc.path.subgraphAll. Neither is tenant scoped.
  • Evaluation order. The guard does not control the order in which Neo4j evaluates predicates. The README records, as an inference that no corpus row demonstrates, that an error raised by a predicate on another tenant's row before the scope filter applies could act as an oracle.
  • Not measured. Latency, Neo4j versions other than 5.26.12, and Cypher 25 syntax.
  • Scope of this article. It describes the public repository at 657c31f. The bypass counts measure the guard as committed at 502b403.
