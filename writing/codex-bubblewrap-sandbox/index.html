Sandboxing Codex CLI with bubblewrap on WSL

A probe on 2026-08-30 showed Codex CLI, started with --sandbox read-only, reading a file at an absolute path outside its working directory and listing the root of an unrelated repository. The codex-sandbox wrapper in agent-controls runs Codex in a bubblewrap mount namespace that holds only the configured root containing the current directory. Paths outside that root, other than a fixed set of system and configured paths, do not exist for the Codex process.

The 2026-08-30 probe: read-only mode left reads open

The header of bin/codex-sandbox records the probe. Codex was started in read-only mode. It read a file at an arbitrary absolute path outside its --cd directory, and it listed the root of an unrelated repository.

The repository draws two conclusions from that result. The --sandbox read-only policy restricts writes and leaves reads open. The project trust settings in Codex's config.toml govern approval prompts and do not set a filesystem scope.

The threat model adds an inference: under the read-only policy, any file the user can read can become part of a Codex prompt, and a prompt leaves the machine. The threat model labels this T3.

The record has gaps. The Codex CLI version used in the probe was not recorded. The record states the outcome; it does not include the command line, the transcript or the paths used. Codex behavior may have changed since that date. Codex was not run for this article. The threat model gives a reproduction procedure whose outcome depends on the installed Codex version.

Inference: the wrapper's boundary does not depend on how a given Codex version applies its own policy, because a path that is not mounted in the namespace does not exist for any process inside it.

Mount layout inside the namespace

The wrapper reads sandbox.conf, finds the configured root that contains the current directory, and starts bubblewrap with the layout below. Only that root is bound. The other configured roots are absent for that session. tool and state paths from the config are bound in every session.

The bubblewrap arguments

base_args builds the fixed part of the command. main appends the tool, state and root binds, the /dev/null masks, the environment changes and the namespace flags.

Bubblewrap applies the mount operations in the order given. The empty tmpfs on $HOME is mounted first. The binds of the root, tool and state paths that lie under $HOME are placed on top of it, and the /dev/null overmounts come last.

The README's dry run prints the full command, one argument per line. The output below comes from a throwaway home directory with the config shown. Arguments are joined per operation, and the throwaway path is written as $HOME.

Refusal outside every root

The wrapper decides whether to start before it builds any bubblewrap argument. find_root compares the physical current directory (pwd -P) with every configured root and returns the longest root that contains it. Roots are resolved with readlink -f when the config is read, so a symbolic link to a directory is compared by its target.

When no root matches, the wrapper prints the configured roots and exits 1. No namespace is created and Codex does not start:

$ cd $HOME/elsewhere && codex-sandbox exec x
codex-sandbox: $HOME/elsewhere is outside every configured root ($HOME/src/my-app $HOME/src/vendor-library $HOME/src/governed-repo); cd into one, or set CODEX_UNCONFINED=1 to bypass

Four further checks stop the wrapper with exit 1:

  1. The current directory is inside a subtree root but outside its listed subtrees. Started in governed-repo/confidential, the message was ... is inside $HOME/src/governed-repo but outside its bound subtrees: docs src tools.
  2. The Codex executable, or the target of its symbolic link, is outside every bound path. A tool line for its install directory fixes this.
  3. The config names / as a root, gives subtrees to an rw root, or gives a subtree that is absolute or contains ...
  4. The config file is missing, has an unknown keyword or a relative path, or leaves no usable root.

A configured root that is not a directory is skipped with a warning; the remaining roots still apply.

What a process inside the namespace sees

For this article the wrapper was also run outside dry-run mode, in the throwaway home directory from the previous section, with the stand-in Codex from the test suite. The stand-in runs its first argument as a shell command. Results on 2026-10-28:

  • cat of a file outside the root: No such file or directory, exit 1.
  • cat .env in the root: Permission denied, exit 1. ls -l .env lists the name as a character device. The file's name stays visible; its content does not.
  • ls -A /: 11 entries: bin dev etc home lib lib64 mnt proc sbin tmp usr. /run and /init are absent.
  • ls -A $HOME: .codex, src and tools, the bound state path and the parents of the bound root and tool path. A planted $HOME/.ssh/id_test did not exist.
  • ls -A /mnt: wsl only, the parent of the bound resolv.conf target.
  • With WSL_INTEROP, WSLENV and GH_TOKEN set in the calling environment, all three were unset inside. A fourth variable, with no unsetenv line, passed through.
  • In a subtree root, ls -A listed docs src tools, and touch docs/x failed with Read-only file system.
  • /proc listed 4 process IDs inside the namespace and 196 on the host in the same run. The process kept the caller's user ID.

Inference: cat .env fails instead of returning an empty file because bubblewrap's --ro-bind does not grant device access on the mount it creates, so the /dev/null device node cannot be opened there. The threat model states the observed result: reads of a masked file fail.

Limits

WSL

  • The Windows drives are hidden by the tmpfs on /mnt. The resolv.conf target is bound back as one read-only file so that DNS resolves. If that target lies under /run on another setup, that one path under /run exists in the namespace.
  • The test for WSL entry points checks that /init is absent and that /mnt holds nothing besides wsl. No test runs a Windows executable from inside the namespace.
  • Inference (untested): if the WSL interop handler is registered with the binfmt_misc F flag, the kernel keeps the interpreter open from registration, and an absent /init would not by itself stop a Windows executable placed in the bound root from reaching it. The unset WSL_INTEROP and the absent /run would then be the remaining barriers. The registration flags were not checked for this article. The threat model lists the same question as untested.

Codex's own sandbox modes

  • The probe covered --sandbox read-only. The repository records nothing about the other Codex sandbox modes.
  • The wrapper passes Codex's arguments through unchanged, except that it adds --skip-git-repo-check to exec in a subtree root. A --sandbox flag therefore still applies, inside the namespace. The repository has no test of Codex's own sandbox running inside bubblewrap.
  • The Codex CLI version in the probe is unknown, so the probe does not show whether current versions still read outside the working directory in read-only mode.

What bubblewrap does not isolate in this configuration

  • The network: --share-net keeps the host network namespace.
  • The user: the process runs with the caller's user ID, and writes in an rw root or a state path land on the host.
  • System calls and resources: the argument list has no --seccomp filter and sets no CPU or memory limit.
  • The terminal: the argument list has no --new-session, which bwrap --help describes as "Create a new terminal session", so Codex keeps the caller's controlling terminal. Whether the running kernel permits terminal input injection was not checked.
  • The kernel and bubblewrap themselves, which the threat model places out of scope.

Masking

  • Masks are computed once, at start, from file names. A secret in a differently named file, a file created later, or a symbolic link stays readable.
  • The search for masked files prunes node_modules, .git, .venv, venv and __pycache__. A .env file inside one of them is not masked. In the 2026-10-28 run, node_modules/pkg/.env was readable inside the namespace. The script header, the threat model and the README list the pruned directories.
  • Masks apply to the bound root only. tool and state paths are not searched.

Bypass and setup

  • CODEX_UNCONFINED=1 is checked before the config is read, so it works from any directory. Run from outside every root with it set, the stand-in Codex could see /init.
  • The wrapper confines Codex only when it is the codex found first on PATH. The real binary run by its absolute path is not confined.
  • The namespace needs unprivileged user namespaces. Ubuntu 24.04 restricts them through AppArmor by default.

Run it

Requirements from the README: bash 4.4 or later, git, Python 3.10 or later, uv, and bubblewrap. The test suite needs no Codex install; it uses a stand-in.

git clone https://github.com/darblinko/agent-controls
cd agent-controls
uvx pytest -q

mkdir -p ~/.config/agent-controls
cp examples/sandbox.conf ~/.config/agent-controls/sandbox.conf   # edit roots and tool paths

CODEX_SANDBOX_DRY_RUN=1 /path/to/agent-controls/bin/codex-sandbox exec "list the files"
