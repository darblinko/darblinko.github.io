62 of 83 prompt change records contain the falsifier keyword

In llm-trading-lab a prompt change is recorded as the text before, the text after, their diff, and a rationale that names the trigger, the expected behavior change and the observation that would show the change was wrong. Across 83 records written from May to October 2026, 95.2% have all four files, 74.7% contain the string "falsif" and 63.9% contain "expected", the lowest of seven checks. The three rationale checks are keyword searches, and the unfilled template passes all three, so these shares measure the form of the records. They do not show that a falsifier was written or that any test was run.

Scope: one package, one export, no prompt text

llm-trading-lab is research tooling for LLM trading agents. Its project page covers the whole repository: the call gate, the walk-forward runner, the leakage audit and the negative results. This article covers one package, src/prompt_history/, which writes a change record for each prompt edit, validates a tree of records against the convention, and counts how many records pass each check.

The counts come from one run of python -m prompt_history index on the prompt history and changelog of a private research repository at revision 27c1a59 (2026-10-21). The export holds counts only. The private tree cannot be regenerated from the public repository, and records written after that revision are not counted.

Neither the repository nor this article contains live prompt text. The one example record in the repository is fictional, and this article does not reproduce its prompt snapshots.

The record format: one folder, four files, one changelog entry

python -m prompt_history record takes the prompt name, a short slug and the two versions of the prompt file. It writes one folder named YYYY-MM-DD_<prompt_name>_<slug> holding four files, and the rationale starts as a template with five headed sections. It refuses a prompt name that is not snake_case, a slug outside 2 to 5 kebab-case words, an edit where before and after are identical, and a folder that already exists.

FieldStored inWhat it is for
Date, prompt name, slugFolder nameDates the change and names the prompt it changed. The index counts records per month and per prompt from the folder name alone.
Beforebefore.mdThe full prompt as the agent saw it before the change.
Afterafter.mdThe full prompt after the change. With the before snapshot it lets the validator recompute the diff.
Diffdiff.patchA unified diff of the two snapshots: the changed lines without the rest of the prompt. The validator compares its added and removed lines with a diff it recomputes, so a snapshot edited after the record was written is reported.
Triggerrationale.mdTemplate text: "Which review, incident or measurement prompted this change."
Enforced rulerationale.mdTemplate text: "The rule the added or changed text is meant to impose." No check reads this section.
Expected changerationale.mdTemplate text: "What the agent should now do differently, stated so it can be counted in the logs."
Falsifierrationale.mdTemplate text: "The observation over the next sessions that would show the change did not work."
Changelog linkrationale.md cross-references and the changelogTies the record to the changelog entry that announced the change. The validator passes a record when its folder name appears anywhere in the changelog text.

The expected change and the falsifier answer different questions. The expected change is a count that shows the edited prompt altered what the agent does. The falsifier is an observation that shows the altered behavior did not serve its purpose. Inference: a change can produce its expected change and still be falsified, which is the case the falsifier exists to catch.

The changelog entry is a separate document with its own template: Files, Trigger, Change, Why, Contradiction check, Validation and Status are required, and Outcome is filled in after at least one session. The repository does not define the Contradiction check field; the example entry fills it with "none found".

Each LLM call made by the live loop is written to a daily markdown trace with its prompt name, payload, raw response, parsed result and token usage, and two review apps show the traces on the price chart. A session review that leads to a prompt change starts a record.

Code covers three steps: writing the record, validating a tree of records, and indexing it into counts. The rationale, the changelog entry and the falsification check are written and done by a person. No code in the repository reads a falsifier or evaluates it against the traces. What the failed checks mean in practice

Each item below is an inference from the field definitions and the counts. None was checked against the 83 records, whose text is private.

  • No "expected" keyword: 30 records (36.1%). The rationale lacks the word, so the template heading was removed or not used. If such a rationale also states no expected change in other words, it gives no count to look for in the traces, and the record alone cannot show whether the edited prompt changed what the agent did.
  • No "falsif" keyword: 21 records (25.3%). The rationale lacks the word and the template's Falsifier heading. If it also names no failure observation in other words, keeping or reverting the change rests on a judgment that the record does not capture.
  • Both keywords present: between 32 and 53 records. 53 contain "expected" and 62 contain "falsif", so at least 32 contain both. The per-record results needed for the exact figure were not exported.
  • No "trigger" keyword in the rationale: 13 records (15.7%). Every changelog entry carries a Trigger label, so the trigger for some of these records may sit in the linked changelog entry. The export does not join records to entries, so this is unmeasured.
  • No Validation field: 35 of 127 changelog entries (27.6%). Those entries do not say how the change was to be validated. The example entry fills the field with paper trading and a reminder to fill Outcome after at least one session.
  • Not linked from the changelog: 4 records. These cannot be found from the changelog by folder name.
  • Diff disagrees with snapshots: 3 to 7 records. A snapshot was edited after the record was written, or the patch was made from different text. The diff then no longer describes the change exactly. The repository's test for this check edits after.md after recording and expects this failure.

The keyword rule bounds what the shares can show. A test in the repository records a change, leaves the rationale as the unfilled template and expects the validator, run without a changelog, to report no problem, because the template's own headings contain "Trigger", "Expected" and "Falsifier". For records written from the template, each share is therefore an upper bound on filled sections. In the other direction, a rationale that states an expected change without the word "expected" counts as failing.

Limits of this result

  • One snapshot of a private tree. The counts describe the prompt history at 27c1a59 on 2026-10-21. They cannot be regenerated from the public repository, and records added after that revision are not in them.
  • Keyword checks. The rationale checks look for three words. An unfilled template passes them, and a rationale that uses other words fails them. The 83 records were not read for this article.
  • No outcomes. The export counts Outcome labels. It does not count falsifiers that were observed, changes that were reverted or changes that were kept. Whether any stated falsifier was ever checked against the traces is not recorded in the repository.
  • No per-record or per-month compliance. Overlaps between checks are given as ranges. The export cannot show whether the share of records with an expected change rose over the six months, or when the private tree adopted the template.
  • Records and changelog are not joined. The link check confirms a folder name appears in the changelog. It does not confirm the linked entry describes the same change.
  • No prompt text. The record structure and the counts are published; the prompts are not. The example record is fictional and is not one of the 83.
