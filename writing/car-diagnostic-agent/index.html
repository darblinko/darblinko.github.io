An AI agent that talks to my car over KWP2000 and UDS

MechanIQ, the Claude agent inside the obd-scanner diagnostic app, never opens the serial port. It calls 18 typed MCP tools; deterministic code builds every CAN frame and checks every request against an allowlist of 16 service IDs. One session on a 2017 Infiniti Q50 found 13 modules and 3 stored codes, and decoded a 21-byte steering record in which 2 of 8 fields are confirmed against independent signals and 6 are labelled as inferences.

The agent calls tools and code builds the frames

obd-scanner is a PySide6 desktop app (Python package q50diag) that reads a car over KWP2000, UDS and OBD-II through an ELM327 or STN USB adapter. MechanIQ is a Claude Agent SDK agent in a side panel of that app. The project page describes the app, its pages and how to run it. This article covers the design decisions behind the agent's access to the car, and what one session on a car recorded.

One diagnostic read on CAN takes several steps. The adapter needs a request header and a receive filter for the module's CAN IDs. A reply longer than one frame needs ISO 15765-2 flow control and reassembly. A module that needs more time answers 7F <service> 78 (response pending), and the request has to be repeated with a longer timeout. Before any of this, something has to decide whether the service ID may be sent at all. In obd-scanner each of these steps is Python code with tests. The agent decides what to read.

The agent never receives a CAN ID or a serial handle. read_module takes a module name such as EPS. raw_read takes a module name and a hex payload such as 21 01, or an adapter command such as ATRV without a module. The tool resolves the name to a request and response ID from the vehicle profile and returns JSON: decoded values with units, codes with their status, or the request and reply as text.

The code shows three reasons for this split.

  1. The adapter has one owner. Session runs every transport call on one worker thread. The GUI pages, parameter polling, the recorder and the agent's tools all submit commands to its queue. Inference: a second process writing to the same serial port would interleave its bytes with the session's AT commands and requests.
  2. Code decides which bytes reach the car. check_request_allowed runs in raw_read before the request is queued, and again inside the transport for every request from any caller. A model can write any hex string; the allowlist decides which ones are sent.
  3. Results are structured, and failures say what to do next. A handler that cannot proceed raises ToolError with an instruction, for example "Not connected to an adapter. Ask the user to connect on the Connect page."

Transport: from a tool call to CAN frames

The adapter is set up once when the port opens: ATE0 ATL0 ATS1 ATH1 ATAT1, then the bus protocol (STP33 or ATSP6 for HS-CAN at 500 kbps), then ATCAF1 ATCFC1 ATD0 ATAL ATFCSM0. With headers on (ATH1) every reply line carries its CAN ID, so elm_parse.py reassembles single, first and consecutive frames per ID and keeps interleaved replies from two modules apart.

For each module request, ElmTransport.request checks the payload against the allowlist, then changes adapter state only where it differs from the last request: ATSH with the request ID, ATCRA with the response ID, the timeout in units of 4 ms (ATST), and flow control. Two details come from Nissan addressing and from the ELM327 command set.

  • Flow control. Nissan modules on this car answer at the request ID plus 0x20; the EPS module uses 742 and 762. A comment in the driver states: "ELM's automatic OBD mapping is unsuitable for Nissan +0x20 addresses". For any pair other than 7E0 to 7E7 with a response ID 8 higher, the driver sets the flow control header itself with ATFCSH, ATFCSD300000 and ATFCSM1.
  • Response pending. After a 7F xx 78 reply the ELM prints its prompt and stops listening. The driver repeats the request once with adaptive timing off (ATAT0) and the longest timeout (ATSTFF: 255 units of 4 ms, 1.02 s), then restores ATAT1.

Adapter commands from the console or from raw_read pass to the adapter with three exceptions in console_command. Input containing a line break or a NUL byte is refused. An empty line is refused, because the ELM327 repeats the last request on an empty line. Nine command prefixes are refused, which the error message calls adapter programming and baud changes: ATPP, ATBRD, ATBRT, STP, STBR, STWBR, STSBR, STRSTNVM and VTUPDATE. The STP prefix also covers the protocol command that the app itself sends at setup. Hex lines typed on the console go through the same allowlist as every other request.

None of the 714 tests needs an adapter. tests/fake_serial.py emulates the byte stream of a vLinker FS, an OBDLink EX and a plain ELM327, and a simulator transport answers for every vehicle profile.

Module discovery follows the same rule. Each of the 15 addresses in the Q50 profile is probed with 3E 00, 10 81 and 21 83 until one gets a positive reply. The remaining IDs from 0x700 to 0x7FF get tester present only; the code comment reads "Unknown addresses get tester present only, so no session is started on them." The sweep never transmits on a response ID or on 0x7DF.

The allowlist call lives in each transport implementation, ElmTransport and SimulatedTransport. The abstract Transport.request states the contract in its docstring, and the parametrized test covers both implementations. Inference: a third transport would need its own call and its own test case.

18 tools in the app's own process

build_mcp_server creates an in-process MCP server named q50 with the Agent SDK's create_sdk_mcp_server. The tools are methods on the running app, and the agent sees them as mcp__q50__<name>. Because they run in the app's process, they read the same parameter store, recorder and event markers that the GUI shows, and their vehicle requests enter the same session queue as the pages' requests.

The handlers run on the SDK's asyncio thread. Every read or change of app state is moved onto the Qt main thread with call_in_main_thread, wrapped in asyncio.to_thread so that neither the Qt thread nor the asyncio loop blocks. Tools whose result arrives as a session signal connect a one-shot catcher, submit the command and wait with a timeout: 8 s for raw_read, 45 s for read_module and 120 s for scan_dtcs.

The guard hook

The runner starts the Claude Code session with permission_mode="bypassPermissions" and one PreToolUse hook. With no permission prompts, the hook decides every tool call. The docstring of guard.py states it: "MechanIQ runs with permission prompts off, so this hook is the hard boundary." The hook is registered without a matcher, so it receives every call. It has rules for 9 tool names (4 write tools, 3 read tools, Bash and PowerShell) and returns no decision for the rest, which includes the 18 q50 tools and Task.

The 7 deny rules account for 36 cases. 22 more are allow cases, which act as controls: a guard that denied everything would fail them. The last 4 test the hook plumbing: other hook events pass through, relative paths resolve against the working directory, unbalanced quotes fall back to text checks, and segments split on separators. The project page charts the deny and allow counts. One of them is the commit git commit -m "fix(mechaniq): push EPS reads earlier; COM5 note; reset --hard docs", whose message contains the words of three deny rules.

The Bash rules work on parsed commands. shell_segments splits a command with shlex into simple commands at ;, |, &, parentheses and line breaks, so quoted text stays inside its argument. For a segment that runs git, the subcommand is found after git's own options, which is how git -C /x push --force is caught. The serial patterns (/dev/tty, /dev/serial, COMn, serial.Serial(, serial_for_url, miniterm) apply to segments that do not run git. Redirect and tee targets are resolved against the working directory and checked as file writes; /dev/null, /dev/stdout, /dev/stderr and $VARIABLE targets are skipped. The secret check runs on the raw text before shlex, with backslashes turned into slashes, because shlex drops the backslashes of an unquoted Windows path. A command with unbalanced quotes falls back to regular expressions for push, discard and serial access.

Each denial names what to do instead. The serial rule returns: "Bash may not open a serial device or adapter port: the q50diag app owns the connection. Use the q50 tools (raw_read, read_module, get_readings) for vehicle access. To search code for this text, use the Grep tool." Inference: the last sentence covers a code search whose text matches a serial pattern, such as a search for /dev/tty; a Grep call for serial.Serial is one of the allowed test cases.

The same docstring states the limit: "The Bash checks are a guard against mistakes, not a sandbox: a script file can still do anything its interpreter allows."

One session on a 2017 Q50: modules and codes

On 2026-10-17 the app was connected to a 2017 Infiniti Q50 3.0t through a vLinker FS r2 adapter (STN1170 firmware v4.3.2) at 115200 baud, about 16 ms per command. The complaint was steering that intermittently feels stiff and sluggish. The car has no DAS: its Drive Mode Selector offers Standard and Sport steering only, and there is no power steering fluid reservoir, so it has a rack electric power steering (EPS) unit.

Every field value in this article comes from docs/q50-findings-2026-10-17.md. That document records what was read and decoded. It does not record which requests MechanIQ issued and which came from the GUI pages or the console, and this article makes no claim about the agent's share of the session.

One session on a 2017 Q50: the steering record

The EPS module answered Nissan local identifiers (21 xx) only; six 22 xxxx ranges returned nothing. The project's research notes state that no public source gives EPS identifiers for the Q50. 21 06 returned a 280-byte block, which the document labels an inference: a stored event history, not decoded.

Limits

Not tested on hardware

  • Field data covers one car, one adapter and one session, on 2026-10-17.
  • The two Mustang S550 profiles (9 modules each) come from public address lists. The repository holds no field capture from a Mustang.
  • MS-CAN on the vLinker FS is untested. The OBDLink EX and plain ELM327 support is tested against emulated byte streams only.
  • The sample rate of the rebuilt Steering page recording on the car is not yet measured.
  • The simulator replays a 90 s drive cycle: idle to 15 s, acceleration to 95 km/h by 40 s, cruise to 70 s, deceleration to 90 s. Apart from the stored EPS record, its values are synthetic and say nothing about the car.

Read-only by allowlist

  • No write, reset, security access, routine, I/O control, download or programming service is on the allowlist. Codes can be cleared only from the Trouble Codes page after a confirmation dialog. The agent has no tool that clears codes.
  • Adapter commands are filtered by a list of refused prefixes, which is a block list. Any AT, ST or VT command outside that list reaches the adapter, including from raw_read.

Inferred fields

  • Six of the eight decoded EPS fields in the findings document are inferences, and their scales are unconfirmed.
  • The steering complaint was not reproduced while EPS data was captured, so no decoded field has yet been observed during a heavy steering event.

The guard hook

  • The hook is designed to catch agent mistakes. A script the agent writes inside the project can do anything its interpreter allows. Reads outside the project are allowed, except of the secret files; one allowed test case reads a dotfile in the home directory. Permission prompts and an operating system sandbox are not used.
  • data-analyst and test-coach are denied the edit tools and apply_change; test-coach is also denied Bash. data-analyst keeps Bash, and a Bash redirect inside the project passes the guard, so its read-only role inside the project rests on its prompt. The disallowed lists omit MultiEdit because the Claude Code CLI bundled with the pinned Agent SDK has no such tool; the guard still checks it as a write tool.
  • The findings document does not record which requests the agent made during the field session.
